# Testing tidyfault

tidyfault ships two implementations of the same API: the R package at the root
of this repository and its Python twin in `python/`. R is the reference. This
page explains how both are tested, how to run the tests, and what to do when
you change something that moves a number.

All commands below are run from the repository root unless a line says
otherwise.

## What is tested and why

| Suite | Framework | Where it lives |
|---|---|---|
| R | [testthat](https://testthat.r-lib.org) 3rd edition | `tests/testthat/` |
| Python | [pytest](https://docs.pytest.org) | `python/tests/` |
| Parity fixtures | JSON written by R | `python/tests/reference/` |

The R suite has one `test-<name>.R` file per area of the package (`equate`,
`gate`, `illustrate`, `mocus`, `plot`, `populate`, `quantify`, `quantify_ci`,
`quantify_if`, `quantify_when`, `simulate`, `workflow`). It checks fault-tree semantics (gate names match whole tokens, a
top event is not a gate, cycles are refused), cut sets, probabilities, and the
error messages users see.

The Python suite checks the twin against R, not against itself. The file
`python/tests/reference/r_reference.json` holds R's own output for a set of
trees (the bundled datasets plus a minimal tree). It is generated by
`python/tests/reference/make_r_reference.R`, and `python/tests/test_core.py`
and `python/tests/test_mocus.py` assert that Python reproduces it. If Python
disagrees with R, the Python is the bug.

## Run the R tests

You need R, the `devtools` and `testthat` packages, and the packages listed
under `Imports` and `Suggests` in `DESCRIPTION`. A compiler toolchain is needed
too, because the package contains C++ code. If something is missing, the first
test run names it. Install it with `install.packages()` and run again.

Run the whole suite:

```
Rscript -e 'devtools::test()'
```

Run one test file. The filter is matched against the file name after
`test-`, so this runs `tests/testthat/test-equate.R`:

```
Rscript -e 'devtools::test(filter = "equate")'
```

Run the full package check (builds the tarball, then checks it, including
tests, examples and vignettes):

```
R CMD build . && R CMD check --no-manual tidyfault_*.tar.gz
```

or, in one step from R:

```
Rscript -e 'devtools::check()'
```

The check ends with a status line. Today it is `Status: 1 NOTE` (the NEWS.md
heading), with 0 errors and 0 warnings. Keep it that way: run the check before
you start so you know the baseline, and do not open a pull request that adds an
error, a warning or a note. The details are in `tidyfault.Rcheck/00check.log`.

## Run the Python tests

```
python -m venv .venv && . .venv/bin/activate && pip install "./python[test]" && pytest python/tests -q
```

This creates a virtual environment, installs the Python package with pytest,
and runs the suite. The package needs Python 3.10 or newer. Afterwards, to run
just one file:

```
pytest python/tests/test_mocus.py -q
```

## What "the twins agree" means

For every function that exists in both languages:

- the function names are the same;
- the argument names are the same;
- returned tables have the same column names, in the same order;
- rows come back in the same order;
- return shapes are the same (a data frame in R is a data frame in Python, a
  single number is a single number);
- probabilities agree to 1e-9 (`pytest.approx(..., abs=1e-9)`).

Where the two disagree, the Python is the bug. The one exception is when R is
itself wrong: then R is fixed first, the Python follows, and any note recording
the deviation is deleted.

Any R change that moves a number, a column, or a row order has to land together
with regenerated fixtures, in the same pull request. Otherwise the Python tests
keep checking the old behavior.

## Regenerate the parity fixtures

`make_r_reference.R` sources the R functions straight from this checkout (so
the fixtures describe the source in front of you, not whatever build you have
installed) and uses the installed `tidyfault` only for the compiled routines
(`mocus_rcpp()`, `concentrate()` and the fast probability code). Install the
current checkout first, then regenerate:

```
R CMD INSTALL .
Rscript python/tests/reference/make_r_reference.R . python/tests/reference/r_reference.json
```

The script needs `dplyr`, `stringr`, `tidyr`, `tibble`, `scales`, `jsonlite`
and `tidyfault`. Then check that Python still agrees:

```
pytest python/tests -q
```

The file records the R version that wrote it, so that one line changes whenever
you regenerate on a different R. If you did not change any behavior, that is the
only line that should differ. You will also see warnings such as `cannot open
compressed file './data/none_outcomes_binary.rda'`. They are expected: the script
looks for optional outcome tables and skips the ones that do not exist.

Never edit `r_reference.json` by hand. Review the diff of the regenerated file
like any other change: every changed number should be one you meant to change.

## How the R test helpers work

`tests/testthat/helper-trees.R` is loaded automatically before every test file
(testthat sources any `helper-*.R`). It defines four small functions, so tests
do not each rebuild the same fixtures:

- `minimal_or_top_tree()` returns a list with `nodes` and `edges` for the
  smallest valid tree: a top event `T` with two children, `A` and `B`. Its
  `type` column is a factor with levels `top`, `and`, `or`, `not`. Pass
  `tr$nodes` and `tr$edges` to `curate()`.
- `strip_outer_parens(s)` trims whitespace and removes any wrapping pairs of
  parentheses from a string.
- `normalize_cutset_token(s)` trims one cut-set string and strips its outer
  parentheses.
- `cutset_signature(cuts)` turns a vector of cut sets such as `"(B * A)"` into
  a sorted, de-duplicated vector of canonical strings (`"A*B"`). Use it to
  compare cut sets from different engines without caring about term order or
  spacing, for example `expect_identical(cutset_signature(a), cutset_signature(b))`.

The larger example trees (`fakenodes`, `db_nodes`, `ai_nodes` and so on) are
bundled datasets in `data/`, so any test can use them directly.

## Add a test

1. Find the file for the function you are changing, `tests/testthat/test-<name>.R`.
   If the function has no file yet, create one with that name.
2. Put the new test next to the tests that are most like it.
3. Write the smallest test that fails without your change. Follow the style
   already in the file: `test_that("a plain sentence saying what is true", { ... })`,
   `=` for assignment, and `expect_*()` functions from testthat 3.
4. Make the test self-sufficient: build its own input (a helper from
   `helper-trees.R` or a tiny tibble in the test), and call `set.seed()` first
   if randomness is involved.
5. Run just that file with `devtools::test(filter = "<name>")`, then the whole
   suite.

If your change affects a function that Python also implements, add or update
the matching test in `python/tests/` and regenerate the fixtures (see above).

### Snapshot tests

Error messages and printed output that users read are checked with
`expect_snapshot()`. The recorded output lives in `tests/testthat/_snaps/`
(currently `populate.md` and `simulate.md`), one file per test file.

When you change a message on purpose, run the tests, review the proposed
change with `testthat::snapshot_review()` (or read the diff of the `.md`
file), and accept it with `testthat::snapshot_accept()`. Commit the updated
`.md` file with your change. A snapshot that changes when you did not mean to
change it is a bug, not noise.

## Continuous integration

GitHub Actions runs the tests for every pull request. Three workflows are
involved:

- `R-CMD-check` runs the full R package check;
- `python-tests` runs the Python suite, including the parity tests;
- a weekly install smoke test installs the package fresh, to catch a
  dependency that broke between releases.

A pull request should be green on all of them before it is merged. When one
fails, run the matching commands above locally to reproduce it.
